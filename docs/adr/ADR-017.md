# ADR-017 — Arnés de ingeniería para agentes

- Estado: propuesta de CHG-026, vigente si el propietario acepta el PR
- Fecha: 2026-11-03
- Cambio: CHG-026
- Aprobación: pendiente del propietario. Este ADR no autoriza merge ni despliegue.

## Contexto

El trabajo que sigue, empezando por `/api/v1/bot`, tiene que pasar por especificación, criterios de aceptación, pruebas primero, CI y revisión humana. Hoy la integración con PostgreSQL solo corre en un workflow acotado a CHG-025, el Gherkin de `docs/04-BDD.md` no se ejecuta, no hay contrato OpenAPI ni piso de cobertura, y el lint no existe.

El repositorio es público y ya contiene CSV con datos personales y un secreto JWT de respaldo en `middleware/auth.js`. Este cambio no reescribe historia ni borra esos archivos.

## Decisión

1. Cada cambio de comportamiento copia `docs/plantillas/` y deja historia, requisito, Gherkin, casos TDD, plan, trazabilidad y registro de decisiones. Un ADR nuevo se publica en `docs/adr/` solo cuando hay decisión de diseño.
2. Los escenarios HTTP de muestra viven en `features/` y corren con `@cucumber/cucumber` 11.3 y Supertest contra el `app` de Express. La serie 13 exige Node 22 o superior; este repositorio fija Node 20 en CI, así que el paquete queda en 11.3. No se convierte el Gherkin histórico completo.
3. La integración usa PostgreSQL 16 como servicio de GitHub Actions, el mismo patrón que CHG-025. Testcontainers queda descartado en este cambio: el entorno de CI no necesita Docker dentro del job y la máquina de desarrollo puede no tener Docker. En local, `TEST_POSTGRES_URL` o `CHG025_TEST_POSTGRES_URL` apuntan a una base cuyo nombre incluye `test`, `ci` o `local`. Sin URL, el caso se omite y el proceso sale en cero. El arnés crea un esquema efímero, siembra solo datos ficticios y lo elimina. No llama a `migrate_pg.js`.
4. La cobertura usa `c8` con piso de 35 % de líneas, 35 % de sentencias, 55 % de ramas y 70 % de funciones. La base medida sin PostgreSQL fue 37.82 %, 37.82 %, 61.3 % y 76.36 %. El piso está debajo de esa base para acusar una caída, no para afirmar que el monolito `server.js` está cubierto.
5. El contrato del API de bots es OpenAPI 3.1 en `docs/api/bot-v1.yaml`. Se valida el documento con `@apidevtools/swagger-parser` y las respuestas de ejemplo con Ajv (JSON Schema 2020). No se monta `express-openapi-validator` en la aplicación: haría fallar peticiones reales y cambiaría el comportamiento. El placeholder `GET /api/v1/bot/health` no está implementado; la prueba de contrato afirma que hoy responde 404.
6. CI corre en cada pull request: ESLint con reglas mínimas (`no-eval`, `no-implied-eval`, `no-new-func`, `no-debugger`) más `node --check`, sin reformatizar el árbol; la suite completa; BDD; el piso de cobertura; el contrato; gitleaks, con `.gitleaksignore` solo para los hallazgos ya presentes; `npm audit --audit-level=high`.
7. Las actualizaciones de la auditoría npm de este cambio son parches transitivos (`body-parser`, `proxy-addr`, `qs`, `undici` y acompañantes) para que el gate de vulnerabilidades altas y críticas sea real. No cambian rutas ni el esquema.

## Alternativas descartadas

- Testcontainers como única forma de levantar PostgreSQL: exige Docker en cada agente y duplica un servicio que CI ya sabe usar.
- Umbral de cobertura por defecto de `c8` (cerca del 90 %): la suite actual no lo alcanza y obligaría a excluir código o a fingir cobertura.
- Middleware de contrato dentro de `server.js`: modificaría respuestas de producción.
- Borrar el secreto de respaldo o los CSV en este PR: el primero cambia el comportamiento de arranque cuando falta `JWT_SECRET`; los segundos están prohibidos de editar aquí. Además, el historial público seguiría conteniéndolos aunque se borraran de la punta.

## Consecuencias

- Un PR de producto sin paquete CHG, sin pruebas en rojo previas y sin CI verde no cumple el flujo.
- Los hallazgos de secreto ya presentes no bloquean CI. Un secreto nuevo sí.
- Hacer el repositorio privado, purgar historia, rotar el JWT y sustituir los CSV por datos ficticios queda como decisión del propietario.
